## 挑战 9（NEW）：上游模型吞噬——「护城河从来不是护城河」

**来源：** 微信视频号「产品老A」—《中间层生死局》五种死法交叉压力测试 (2026-06-21)。

**核心论点：** AI 中间层的真正威胁不是同层竞品，而是上游模型能力的进步速度 > 中间层建护城河的速度。

```
中间层五种死法 → Patent MCP 映射：

① 套壳 → 模型一个 Feature 就灭了你
   └─ Gemini 原生支持专利查询。web scraping 路径归零。⚠️

② 同步层 → 任何一端接入模型就不需要中间人
   └─ Google 官方 BigQuery MCP + Gemini。Agent 直接写 SQL。⚠️

③ 翻译 → 模型自己就是通用翻译器
   └─ ✅ 不命中。Patent MCP 不做翻译/NLP。

④ 拼装/编排 → Agent 自己做 tool chaining
   └─ ✅ 不命中。3 工具原子化，不帮 Agent 做编排。

⑤ 数据搬运 → 数据源直接开放 API/MCP
   └─ Google 提供官方 Patents MCP。⚠️
```

**判定：** 5 条中 2 条不命中，3 条部分命中。上游吞噬不是「会不会」，是「什么时候」。

**防御手段（有限）：**
- 坑位记忆（CN CPC偏差、中文编码、Web→BQ回退）— 经验壁垒，非技术壁垒
- CN 数据深度（BigQuery CN 5400万条）— Google 可以做
- 结构化输出（Pydantic → Agent 零损耗消费）— Gemini 原生也能做到

**反方判词：** 「你的护城河从来就不是护城河，它只是一个等待被填的缺口。」这句话对 Patent MCP 尤其准确。

## 薄层的反方反驳

SQLite、curl、jq 都薄。薄到极致 = 没人想重写。884行背后的坑位记忆（CN CPC偏差、中文编码、Web→BQ回退、claims ORDER BY cast）重写者也要踩一遍。

## 避免失败的路径

12个月内完成心智占领（「专利 MCP = deeparchi」），在此期间积累数据深度/社区/集成。

应对上游吞噬策略：心智占领 > 收费。详见 docs/pricing-design.md § 九。
